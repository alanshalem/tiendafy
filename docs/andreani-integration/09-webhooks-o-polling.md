# 09 — Webhooks o polling

Responde la pregunta 22 del checklist.

## 9.1 Sí hay webhook, pero funciona al revés de lo que esperás

🟢 **OFICIAL** — [developers.andreani.com/documentacion](https://developers.andreani.com/documentacion), sección *"Sending the movements generated by the shipments to a Web Service / API"*, textual:

> "Sending the movements generated by the shipments to a Web Service / API. **The definition of the request, both the properties and the format of the data to be sent, is the responsibility of the client.** You can count on security: Basic Authentication, OAUTH, OAUTH2, etc."

Y en su tabla de configuración:

| Ítem | Valor documentado |
|---|---|
| Productive URL | `A Definir por el cliente` |
| QA URL | `A Definir por el cliente` |
| Method | `A Definir por el cliente` |

**Traducción:** Andreani **no publica un contrato de webhook**. Andreani se adapta al endpoint que vos definís. Vos decidís URL, verbo, formato del body, nombres de las propiedades y el mecanismo de autenticación. Ellos lo implementan del lado suyo.

Es lo opuesto al modelo Stripe/Mercado Pago. Tiene una ventaja enorme (podés diseñar el contrato que te convenga) y una desventaja igual de grande: **no es self-service**. Se configura con Andreani, endpoint por endpoint, en el onboarding.

## 9.2 Payload documentado

🟢 Campos que Andreani declara que puede enviar:

| Campo | Descripción oficial |
|---|---|
| `idAndreani` | Código de seguimiento dentro de los sistemas de Andreani |
| `idCliente` | Código de seguimiento dentro del sistema del cliente |
| `idTraza` | **Identificador único del movimiento en los sistemas de Andreani** |
| `event` | *Client Code 1* |
| `reason` | *Client Code 2* |

🟢 Y aclara: *"the names of the properties can be changed by those defined by the client"*.

### Lo que este payload nos dice

**`idTraza` es la clave de idempotencia.** Es literalmente *"identificador único del movimiento"*. ⛔ Andreani no lo declara como idempotency key, pero es exactamente eso y hay que usarlo así.

**`idCliente` viene de vuelta.** Es el mismo valor que enviamos en `bultos[].referencias[meta=idCliente]` al crear la orden. Eso permite correlacionar el evento con la orden de Tiendafy sin depender de una tabla de lookup por `numeroDeEnvio`. **Poblarlo bien en la creación es lo que hace útil al webhook.**

**`event` y `reason` son "Client Codes".** Este es el hallazgo más revelador de todo el relevamiento: Andreani **mapea sus estados internos a códigos que define el cliente**. O sea que durante el alta del webhook, Andreani te tiene que mostrar su catálogo completo de estados y motivos para que vos definas a qué código propio se traduce cada uno.

> **Consecuencia estratégica:** el alta del webhook no es solo una funcionalidad. **Es la vía por la que se consigue el catálogo de estados (GAP-02).** Aunque el equipo decidiera arrancar con polling, conviene iniciar la conversación del webhook temprano solo para obtener la tabla.

## 9.3 Lo que el webhook NO tiene

| Aspecto | Estado |
|---|---|
| Firma HMAC / secreto compartido | ⛔ **No existe.** La doc no menciona firma ni header de verificación |
| Payload JSON de ejemplo | ⛔ No publicado |
| Política de reintentos | ⛔ No documentada |
| Garantía de orden de los eventos | ⛔ No documentada |
| Idempotencia declarada | ⛔ No declarada (pero `idTraza` sirve) |
| Timeouts esperados | ⛔ No documentados |
| IPs de origen | ⛔ No publicadas |
| Panel de auto-registro | ⛔ No existe |

**La seguridad es la que vos definas en tu endpoint.** La doc dice: *"You can count on security: Basic Authentication, OAUTH, OAUTH2, etc."*

## 9.4 Diseño del receptor de webhook

Como el contrato lo definimos nosotros, lo definimos bien.

### Contrato propuesto para Andreani

```
POST https://api.tiendafy.com/webhooks/carriers/andreani
Authorization: Basic base64(andreani-prod:{secreto-largo-y-rotable})
Content-Type: application/json

{
  "idAndreani": "360000000036820",
  "idCliente":  "TF-042-98231",
  "idTraza":    "a1b2c3d4-...",
  "event":      "EN_DISTRIBUCION",
  "reason":     "",
  "timestamp":  "2026-08-21T14:32:10-03:00"
}
```

Decisiones y por qué:

| Decisión | Razón |
|---|---|
| **Basic Auth con secreto largo** | Es lo más simple que Andreani soporta. OAuth2 agrega piezas móviles sin beneficio real acá |
| **Un endpoint por carrier**, no genérico | Cada carrier tiene su formato. Un endpoint genérico con `if carrier ==` envejece mal |
| **Pedir `timestamp` explícito** | Sin él no se puede ordenar ni detectar eventos viejos. Andreani lo puede agregar porque el contrato es nuestro |
| **Pedir `event`/`reason` como códigos estables**, no como texto libre | Los textos cambian; los códigos no |
| **HTTPS obligatorio, secreto rotable** | Y con soporte de **dos secretos válidos a la vez** durante la rotación, porque el cambio del lado de Andreani no es instantáneo |
| **Whitelist de IPs de origen** si Andreani las provee | Capa extra. ⛔ No están publicadas: pedirlas |

### Procesamiento: recibir rápido, procesar después

```mermaid
sequenceDiagram
    autonumber
    participant AND as Andreani
    participant WH as Webhook endpoint (.NET)
    participant PG as PostgreSQL
    participant MQ as RabbitMQ
    participant W as TrackingWorker
    participant NOTI as Notificaciones

    AND->>WH: POST /webhooks/carriers/andreani (Basic Auth)
    WH->>WH: Valida credencial y forma del payload
    alt Auth inválida
        WH-->>AND: 401
    end
    WH->>PG: INSERT tracking_events_raw (idTraza UNIQUE)
    alt Violación de unicidad (duplicado)
        WH-->>AND: 200 OK
        Note over WH: Idempotente. No re-encola.
    end
    WH->>MQ: publish TrackingEventReceived{idTraza}
    WH-->>AND: 200 OK
    Note over WH,AND: Objetivo: responder en menos de 200 ms.<br/>Nunca procesar de forma síncrona.

    MQ->>W: consume TrackingEventReceived
    W->>PG: Resuelve parcel por idAndreani (o idCliente)
    W->>W: Mapea event/reason → estado neutral
    alt Estado desconocido
        W->>PG: Guarda como UNKNOWN
        W->>NOTI: Alerta al equipo de plataforma
    else Estado conocido
        W->>PG: Actualiza parcel + recalcula estado del shipment
        opt El estado es notificable
            W->>NOTI: Email / push al comprador
        end
    end
```

**Reglas del receptor:**

1. **Responder 200 lo antes posible.** Validar, persistir crudo, encolar, responder. Todo lo demás es asíncrono. Un receptor lento provoca reintentos y timeouts del lado del emisor.
2. **Idempotencia por `idTraza`** con constraint único en la base:
   ```sql
   CREATE UNIQUE INDEX ux_tracking_raw_idtraza
     ON tracking_events_raw (carrier_code, id_traza);
   ```
   Un duplicado devuelve 200 sin reprocesar. Si Andreani reintenta, no pasa nada.
3. **Persistir el payload crudo completo** en `jsonb` antes de interpretarlo. Cuando aparezca un estado nuevo, el histórico ya está guardado y se puede reprocesar.
4. **Nunca asumir orden de llegada.** Ordenar por `timestamp` al reconstruir el historial, y al actualizar el estado del parcel **rechazar retrocesos**: si llega un evento más viejo que el estado actual, se guarda en el historial pero no cambia el estado vigente.
5. **Nunca devolver 4xx por un estado que no entendemos.** Un `event` desconocido es un 200 con alerta interna, no un error. Si devolvés 400, Andreani reintenta para siempre un evento que nunca vas a poder procesar.

## 9.5 Estrategia de polling (fallback y complemento)

El webhook depende de una configuración manual con Andreani que puede demorar. **El polling tiene que existir igual**, por dos razones: es lo que desbloquea el tracking en Fase 2 sin depender de Andreani, y es la red de seguridad si el webhook se cae en silencio.

### El problema

⛔ `GET /envios` (masivo) **no tiene filtros documentados**. Si eso es literal, el polling tiene que ser **envío por envío** contra `GET /envios/{n}/trazas`, lo que escala pésimo: 1.000 envíos activos = 1.000 llamadas por ciclo.

**Confirmar los filtros de `/envios` es lo que decide si el polling es viable a escala.** Si acepta `contrato` + `fechaDesde`, el problema desaparece.

### Diseño con frecuencia adaptativa

No todos los envíos merecen la misma atención. Un envío recién despachado cambia poco; uno en reparto cambia en minutos.

| Estado del parcel | Frecuencia | Razón |
|---|---|---|
| `CREATED` (sin trazas) | cada 6 h | Todavía no pasó nada |
| `DISPATCHED` / `IN_TRANSIT` | cada 3 h | Cambios espaciados |
| `OUT_FOR_DELIVERY` | **cada 30 min**, solo 08:00–21:00 ART | Es cuando el comprador mira el tracking |
| `DELIVERY_ATTEMPT_FAILED` | cada 2 h | Puede haber reintento el mismo día |
| `AVAILABLE_FOR_PICKUP` | cada 12 h | El comprador retira cuando puede |
| **Terminal** (`DELIVERED`, `RETURNED`, `LOST`) | **nunca** | Ver abajo |
| Sin cambios hace más de 20 días | **nunca** + alerta | Envío trabado: requiere intervención humana, no más polling |

**Cómo evitar consultar envíos ya entregados:** un índice parcial que solo indexa los activos, y que la query del job usa directamente.

```sql
CREATE INDEX ix_parcels_polling
  ON parcels (next_poll_at)
  WHERE status NOT IN ('DELIVERED','RETURNED_TO_SENDER','LOST_OR_DAMAGED','CANCELLED');
```

El job levanta `WHERE next_poll_at <= now()` sobre ese índice, y **cada consulta recalcula `next_poll_at`** según el estado resultante. Un envío entregado sale del índice solo, sin necesidad de limpieza.

### Job de polling

```
Cada 15 minutos:
  1. SELECT parcels WHERE next_poll_at <= now() LIMIT 500  (por tenant, round-robin)
  2. Agrupar por tenant (un token por tenant)
  3. Consultar con concurrencia limitada (bulkhead de 5 por tenant)
  4. Por cada respuesta:
       - Deduplicar eventos contra los ya persistidos
       - Publicar en RabbitMQ solo los eventos nuevos
       - Recalcular next_poll_at
  5. Registrar métricas: envíos consultados, eventos nuevos, errores, latencia
```

**Round-robin por tenant** es importante: un tenant con 10.000 envíos no puede monopolizar el job y dejar sin tracking a los demás.

### Deduplicación en polling

Las trazas **no traen id de evento**. La clave de deduplicación es la tupla:

```
(numeroDeEnvio, Fecha, EstadoId, MotivoId)
```

Hasheada y guardada con constraint único, igual que `idTraza` en el webhook. Ambos caminos escriben en la misma tabla `tracking_events_raw`, con la columna de dedup poblada según el origen. Así, cuando el webhook se active, los dos mecanismos conviven sin duplicar nada.

## 9.6 Convivencia de webhook y polling

No son excluyentes. El diseño correcto los usa juntos:

| Mecanismo | Rol |
|---|---|
| **Webhook** | Camino principal. Baja latencia, bajo costo |
| **Polling degradado** | Red de seguridad. Con webhook activo, bajar la frecuencia a **1 vez por día** por envío activo |
| **Alerta de silencio** | Si no llega ningún webhook en 2 h en horario hábil, alertar: probablemente se cayó la integración del lado de Andreani |

La alerta de silencio es la pieza que más falta en las integraciones de webhook. Un webhook que deja de llegar no genera ningún error: simplemente nada pasa, y te enterás por un cliente enojado tres días después.
